# 全站同步与交互性能优化

本功能基于 `5a5d98951bb085be3781f6c22eb00f90b630c0d2` 开发。状态为功能完成、待集成；本文中的测量来自本机合成数据，没有正式上线后的性能录制。

## 问题证据

用户提供的约 70.62 秒 Chrome Performance 录制显示，共用业务同步监听的全量序列化调用链累计约 40.83 秒，JSON.stringify 所在 map 回调约 40.07 秒，其中自身耗时约 21.24 秒。垃圾回收累计约 15 秒；一次 pointerdown 在主线程排队约 2.847 秒，而事件处理本身约 1.34 毫秒。这能解释跨页面点击、输入和弹窗一起停顿。

原监听把全部已缓存业务记录的 JSON.stringify 放在响应式 getter 中，使用 deep + flush:sync。任意相关变化和 applying 状态切换都可能重新扫描全部记录，还会为序列化读取的大量属性建立响应式依赖。关键词监听同样同步扫描全部关键词。

录制中的接口等待响应头约 0.772—3.060 秒；其中部分响应到达后又被忙碌的渲染线程延迟处理。此次优化针对已证实的前端阻塞；没有据此断言服务器延迟已消除或需要升级机器。

## 实现

- 新增 workspace-change-tracker.ts：集合只观察成员与记录身份，每条记录独立观察嵌套修改，使用 Vue pre 队列合并同一轮修改。序列化快照在响应式 getter 外通过 toRaw 读取，只处理变动记录。
- 服务端回读前同步捕获将被更新的记录，避免同一轮事件中的本地修改尚未进入批处理队列就被覆盖。回读成员变动静默接入；已知快照与待保存补丁继续区分服务端数据、本地编辑和失败重试。
- 保存和异步回读前等待已排队的修改处理。关键词待保存数据使用独立快照，保存中的请求对象不会被第二次嵌套编辑改写。作用域重置时释放旧记录监听。
- applyWorkspaceRecords 和列表 hydrate 每批建立一次 ID 索引，替代对每条回读记录重复 find。保存确认每批只生成一次成员映射，配置回读直接定位配置对象。
- 同一缓存分页结果避免重复 hydrate；切换、停用及清空列表后正确恢复。原有请求取消、用户缓存隔离、后台刷新保留可交互列表的行为继续生效。

本地补丁合并、详情不被列表摘要截断、监控/任务作用域、legacy 同步及连接凭据排除均有相关回归覆盖。没有修改服务端、数据库结构、迁移、依赖或正式任务。

## 性能对照

同机、同一 Vitest 合成用例，分别运行基线与候选的实际 cloud-workspace 模块；只替换 session、state 和 API。缓存 600 条商品，每条含 96 项嵌套证据，每次更新其中 20 条并等待 nextTick，连续执行五次。自定义 toJSON 统计未修改记录的序列化次数；统计函数本身会产生额外开销。

| 指标 | 原代码 | 优化代码 |
| --- | ---: | ---: |
| 五次刷新平均耗时 | 419.36 ms | 16.16 ms |
| 五次刷新中其余 580 条记录的序列化次数 | 2,900 | 0 |
| 首次一次性接入全部 600 条记录 | 410.19 ms | 472.09 ms |

该合成场景的刷新平均耗时降低约 96.1%。首次大量记录接入需创建独立监听，因此一次性接入 600 条的初始化稍慢；正常分页通常分批接入。成员映射仍会遍历记录 ID，发生修改的单条大记录仍需深度观察和快照，不声称复杂度或内存占用为常数。

计时来自一次本机对照的五次刷新，未设硬件时间阈值，也不代表线上所有操作会降至 16 毫秒。真实数据分布、接口耗时和浏览器缓存会影响最终结果。功能回归以“刷新 20 条时其余 380 条载荷读取次数为零”验证优化机制，避免依赖机器速度。
