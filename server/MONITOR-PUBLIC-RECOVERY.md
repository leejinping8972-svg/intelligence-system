# 独立站监控失败恢复与公开诊断

## 当前问题与新行为

原监控同一对象每天只运行一次，首个目录请求返回429后结束；当天重新开关也不会续抓。HTTP429表示限流，服务端可用Retry-After指定等待时间，见[RFC6585第4节](https://www.rfc-editor.org/rfc/rfc6585#section-4)。它本身不能证明具体由IP、请求频率还是站点防护规则造成。

本功能让已开启的官网监控在当天冷却后自动恢复未完成页面；暂停对象可由管理员点击“仅恢复官网”发起一次续抓，保持暂停配置。页面显示冷却截止时间（北京时间）、剩余请求数、需要检查来源等原因。

- 429/403默认等待30分钟，同一URL连续失败按指数延长；5xx/超时默认5分钟。优先遵守更长的Retry-After。单日最多3轮恢复，所有轮次累计在原对象的每日请求预算内；耗尽后等待下一日计划。目标域名共享冷却时间。
- 不立即反复请求被限流的接口。失败URL留在队尾，冷却结束后先尝试Sitemap、商品列表、首页等其他公开入口。Shopify商品目录每页50项，降低单次响应大小；实际商品按原流程持久化，首次不完整扫描不伪造“新品”。
- 动态HTML可调用已有本地浏览器渲染，每天最多2页；单页最多12个资源、6MB、30秒，预算中的一次浏览器页面会带来这些有界资源GET。浏览器仍使用原公开页面读取器，没有更换出口IP，不保证能通过WAF。验证页、持续空的动态页面、401、浏览器403等保留失败并提示检查来源，不假装成功。
- 恢复轮次只运行官网商品通道，保留原广告通道结果；不重跑广告或Semrush，不调用Firecrawl等付费备用服务。中断且请求结果未知的运行仍不自动重放。
- 已存在的429失败可根据完成时间计算保守冷却，部署后不必等第二天才恢复。恢复上限、预算或需人工检查的条件仍有效。每天原计划继续按现有规则执行。

## 独立脚本

从项目目录运行（Node依赖需已安装）：

```powershell
node server/public-site-probe.mjs --url https://example.com --state .artifacts/example-public.json --max-requests 3 --shopify
```

只有确认为Shopify时使用`--shopify`。每次默认最多3页，可设1～10页；同一检查点每日累计最多10次。失败和已读商品都保存到检查点，再运行同一命令可续抓；在冷却中会立即返回`cooldown`且不发请求。应为每个站点固定一个检查点，勿通过换文件反复重试。

动态页面需要浏览器时加`--browser`。服务器沿用已安装的Chromium；Windows可显式指定本机Edge，例如：

```powershell
node server/public-site-probe.mjs --url https://example.com --state .artifacts/example-public.json --max-requests 1 --browser --browser-executable "C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"
```

脚本只读公开网页，不连接业务数据库，不使用业务Key，不写入系统商品库。终端输出状态、请求数、商品数、下次时间和错误；完整公开商品保存在本地检查点。检查点使用独占锁，防止并发超量；异常进程遗留的`.lock`需先确认旧进程已结束再处理。计数在调用前保存，崩溃也不把已用额度当作未用。

如果仍然429/403，应根据脚本在目标部署环境的结果调整公开来源、等待更长时间，或申请站点允许的API/访问方式。此脚本不是验证码或任意爬虫防护的保证绕过方案。

## 验证与交付边界

开发使用合成站点、假采集器和隔离内存PostgreSQL覆盖：429与Retry-After、当天自动/手动恢复、跨域限制、累计预算、暂停对象、权限、动态渲染、验证页、检查点与零付费通道重跑。原竞品与站点备用测试继续运行，MySQL沿用现有隔离CI入口。

只在本机做了2次免费公开Sitemap GET（ambrosiacollective.com），可读XML；未查询其完整商品，不代表腾讯云出口可访问，也不能据此宣称正式失败已恢复。未读取真实Key、连接正式业务库、启用正式计划或部署。代码与脚本完成后由独立集成发布会话取本分支提交验证上线。
